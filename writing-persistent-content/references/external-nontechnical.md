# External nontechnical writing

Write for product users or a general audience who should not need internal or
developer context to understand the text.

## Reader task

- Lead with the user's goal, available action, current state, or consequence.
- Use stable product vocabulary and the same labels the interface uses.
- Replace implementation terminology with behavior the reader can observe or
  act on.
- Introduce only the detail needed to make a decision or complete the task.
- Keep related actions, states, and limitations together.

## Product and interface copy

- Make controls describe the action they perform.
- Make status text describe the current state.
- Make errors state what happened and the next available action when one
  exists.
- Do not blame the user or describe an error as easy, obvious, or simple.
- Use the product's design system and UX-writing conventions for labels,
  dialogs, notifications, onboarding, and empty states.
- Check copy in its rendered component. Available space, nearby controls, and
  preceding text determine what the string needs to carry.

## Published prose

- Use descriptive headings and links.
- Keep terminology and capitalization consistent across related surfaces.
- Use literal language for instructions, limitations, pricing, permissions,
  and safety information.
- Avoid jargon, unexplained abbreviations, idioms, cultural references, and
  figurative language that carries required meaning.
- Preserve qualifications that affect availability, eligibility, cost,
  privacy, or user action.
- Do not present planned behavior as currently available.

## Select the primary authority

| Artifact | Primary style source |
|---|---|
| Interface text | Product design system and UX-writing guidance |
| Help or support content | Product terminology and support-content guidance |
| Product website | Brand and content strategy |
| Marketing material | Approved marketing brief and claims |
| Policy, privacy, or regulated text | Legal and compliance guidance |

Use technical documentation guidance only for documentation mechanics that the
primary source does not cover. Do not make interface or marketing copy sound
like developer reference material.
